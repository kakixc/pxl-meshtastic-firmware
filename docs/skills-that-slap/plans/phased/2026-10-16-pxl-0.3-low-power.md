# Build PXL 0.3 low-power firmware for Heltec V3

This ExecPlan is a living document. Keep `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` current. It follows `C:\Users\PXL\.agents\PLANS.md` and is also the phased implementation plan. Execute the phases in order; do not infer a power-consumption claim from a successful compilation.

## Purpose / Big Picture

An owner of a Heltec V3 should be able to install a normal PXL Meshtastic 0.3 `update.bin` based on official Meshtastic `v2.7.26.54e0d8d`, retain their configuration, use the PXL 0.2 display features, and obtain a firmware build capable of ESP32-S3 dynamic light sleep. USER short presses should still advance the screen, and long or repeated presses should keep their Meshtastic actions. The firmware must continue to use the official radio, routing, cryptography, region, and transmit-power implementation. The build must produce reviewable GitHub Actions artifacts without publishing a release. Actual battery improvement remains an unverified hypothesis until measured on hardware.

## Surprises & Discoveries

- The PXL repository stores an approximately 800-line Python patcher inside `.github/workflows/build.yml` rather than storing a Meshtastic source fork. It edits only `userPrefs.jsonc` and three graphics files for PXL 0.2.
- The official 2.7.26 tag pins PlatformIO `espressif32@6.13.0`, which selects Arduino 2.0.17. The default installed ESP32-S3 Arduino SDK configuration has `CONFIG_PM_ENABLE` disabled, so copying PM calls alone cannot enable dynamic sleep.
- The M1NL stable branch reports version 2.7.19 and uses a separately built Arduino 2.x package. PR #11702 targets later `develop` with Arduino 3.x. Neither whole firmware tree can replace the official 2.7.26 base.
- In 2.7.26, Heltec V3 USER is GPIO 0. `ButtonThread` uses `OneButton` with a 1 ms debounce and 20 ms click interval when a screen exists. Ordinary light sleep detaches the normal GPIO handler. This is a plausible short-press loss point, not a confirmed root cause.
- The first local build attempt failed before compilation because PlatformIO could not write to its home directory. After granting the build tool its own directory, package downloads started. The later local build was intentionally interrupted after the user requested the phased workflow; it yielded no compile result.
- The resumed Windows build resolved libraries and reached C++ compilation, but the restricted execution sandbox prevented `xtensa-esp32s3-elf-g++.exe` from starting with `Illegal System DLL Relocation`. A direct `--version` check succeeds outside that sandbox; the same local PlatformIO build is now running there. WSL is denied and the Docker daemon is unavailable.
- The unrestricted local baseline build succeeded in 459.80 seconds and generated `firmware-heltec-v3-2.7.26.54e0d8d.bin` (2,115,136 bytes) plus a separate factory image. It validates compilation of official 2.7.26 with the retained PXL 0.2 patch, not dynamic sleep.
- Manual GitHub Actions run `https://github.com/kakixc/pxl-meshtastic-firmware/actions/runs/38942350678` passed all `prepare` and `build` steps for commit `c93c0d2` on the feature branch and uploaded artifact `pxl-heltec-v3`. No release job ran.
- The M1NL Arduino 2.x release archive is 259,831,357 bytes. Its SHA-256 is `ea294c5e5bce958378b407306ad2b29ad691e42eacb6d9197d583fca28e7595f`, matching GitHub's asset digest. Its ESP32-S3 `sdkconfig` has `CONFIG_PM_ENABLE=y` and `CONFIG_FREERTOS_USE_TICKLESS_IDLE=y`.
- The PM-framework-only Heltec V3 build succeeded in 442.12 seconds and produced a 2,137,536-byte application image. It confirms compiler and linker compatibility; no dynamic sleep logic was present in that image.
- Manual GitHub Actions run `https://github.com/kakixc/pxl-meshtastic-firmware/actions/runs/38999865180` passed for PM-only commit `8b18afd` and uploaded the Heltec V3 artifact without publishing a release.
- On official 2.7.26, `setBluetoothEnable(false)` does not actually deinitialize an active NimBLE controller; the code says that re-enabling it after shutdown requires reboot. ESP-IDF 4.4 documents that Bluetooth may hold a `ESP_PM_NO_LIGHT_SLEEP` lock. Therefore PM capability does not ensure automatic light sleep with Bluetooth active, and forcing controller shutdown could break reconnection. Record Bluetooth-on and Bluetooth-off separately during hardware tests.
- Official `PowerFSM_setup()` only schedules its light-sleep state when power saving is enabled (or the node is a router) and Wi-Fi/tracker constraints permit it. PXL 0.3 should respect that configuration rather than silently overriding user settings.
- `InputBroker::handleInputEvent()` drops input after waking an off screen. A Heltec V3-only exception for a short `INPUT_BROKER_USER_PRESS` is needed so one short press can advance the frame; long and repeated press actions remain unchanged.
- The first Dynamic Light Sleep draft compiled locally in 600.09 seconds, and a CPU-frequency tweak rebuilt in 220.64 seconds. These builds prove syntax/link compatibility only. The draft changed USER's CHANGE ISR into a level trigger through `gpio_wakeup_enable`, while RadioLib's `detachInterrupt()` can disable DIO1 wake after its first IRQ. It also attempted an FSM transition in `lsEnter` before arduino-fsm assigned the LS state. It is unsafe to distribute as a low-power build.
- A direct `InputBroker` pass-through for screen-off USER presses also fails: `Screen::setOn(true)` queues SET_ON and `Screen::handleInputEvent()` rejects input until the command runs. The corrected draft queues `showNextFrame()` behind SET_ON, but it has not been hardware-tested.
- The initial PM workflow hashed one downloaded archive while PlatformIO fetched the package independently. The workflow now points PlatformIO at the already checksum-verified local archive. Manual Actions run `39001031077` passed all steps, and its `PXL.2-update.bin` SHA-256 matched the packaged checksum: `bb14fd2588461a3a6c1f8e2cde253272c07f9edf71c71de332ea299e08e93649`.
- M1NL configures RTC EXT1 active-low wake for Heltec V3 USER (GPIO0) and RTC EXT0 active-high wake for SX1262 DIO1 (GPIO14). This avoids overwriting the ordinary digital interrupt type, but its RTC hold/mux reset happens when its application PM lock is reacquired. Automatic wake can run handlers before that reset; the timing and repeated button/radio events require device tracing before a runtime patch is enabled.
- ESP-IDF 4.4.7 explicitly requires `rtc_gpio_deinit()` after EXT0/EXT1 wake before digital GPIO reuse, and `rtc_gpio_hold_dis()` may also be needed. No general automatic-wake callback is exposed by the installed Arduino 2.x SDK headers. A direct RTC port therefore risks handling button/radio events while their pins remain in RTC mode; keep it out of the build until this is resolved.
- Source-level wake scheduling audit: `RadioLibInterface` is a `NotifiedWorkerThread` on `mainController`, not an independent FreeRTOS task. The main loop can block on `mainDelay`'s semaphore, while RTC EXT0/EXT1 wake does not signal that semaphore. Digital GPIO interrupts are gated during automatic Light Sleep. Restoring pins at the start of `esp32Loop()` would precede the main-controller callbacks, but the loop may resume only at a later timeout, after a short press is released. The radio missed-IRQ fallback is polled no more than once per second. M1NL's `gpioReset()` also resets all RTC/output pads; a board-specific port should restore only USER and DIO1. This is an unresolved runtime design issue, not a measured regression.
- An RTC EXT1 USER / EXT0 DIO1 prototype now compiles with a pin-specific reset, a call to the existing RadioLib RX_DONE backup after EXT0, and an active-transmission veto. The first three local builds passed in 329.42, 90.41, and 85.52 seconds. `PowerFSMThread` normally runs every 100 ms; the experimental patch lowers its LS-state interval to 25 ms, with an unmeasured CPU current cost. A released short press can still be lost before the wake reason is handled, and `esp_sleep_get_wakeup_cause()` may refer to a prior cycle when automatic PM sleep did not happen. These risks prevent putting this patch in the default CI image.
- The next RTC prototype checks the live RTC USER/DIO1 level before accepting an EXT1/EXT0 wake cause, reducing false transitions from a stored prior wake cause. ESP-IDF 4.4.7 documents that held input pads can still reflect input changes. The exact-tag patch application and a 263.30-second local compile passed. This is still a source-level mitigation: a very short released press, repeated DIO1 signaling, and the 25 ms polling energy cost remain physical-test risks.

## Context and Orientation

The repository root contains `.github/workflows/build.yml` and `README.md`. The feature-branch workflow downloads the exact official tag, initializes `meshtestic` and `protobufs`, runs `scripts/apply_pxl.py`, builds only `heltec-v3`, and packages a normal `*-update.bin` application artifact. The main-branch workflow also builds six other boards and publishes a release; main has not been modified.

Meshtastic's `src/PowerFSM.cpp` decides whether the device is on, dark, or in its existing light-sleep state. `src/sleep.cpp` configures wake sources and calls the ESP-IDF sleep API. `src/input/ButtonThread.cpp` classifies button presses; `src/input/InputBroker.cpp` attaches USER GPIO interrupts and routes the resulting events to `src/graphics/Screen.cpp`. The Heltec V3 board variant is `variants/esp32s3/heltec_v3/platformio.ini` plus `variant.h`. These Meshtastic paths exist in the downloaded upstream checkout, not in this PXL repository. A patch file in this repository must therefore apply to the exact upstream tag during each build.

The term *Power Management* (PM) means the ESP-IDF component that changes CPU frequency and permits FreeRTOS to enter light sleep while idle. A PM lock temporarily prevents sleep during critical work. The *update image* is the application binary flashed without intentionally erasing the configuration partitions; a factory image is a separate installation artifact. A successful compile proves symbol and linker compatibility, not that PM is active at runtime or that current draw has improved.

## Phasing strategy and file map

Use a **risk-first** sequence. Phase 1 proves that PXL 0.2 survives the exact official tag and that the build is safe to run. Phase 2 isolates the toolchain unknown. Phase 3 changes runtime behavior only after the framework is demonstrably PM-capable. Phase 4 tests the assembled firmware and separates software evidence from physical measurements.
